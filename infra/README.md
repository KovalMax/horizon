# Horizon infrastructure

Run local commands from the repository root with `make`. The development
targets keep the repository root as the Compose project directory so moving
the manifests does not rename the running project or its volumes.

| Manifest | Purpose |
| --- | --- |
| `compose.dev.yaml` | Local development stack (`make up`, `make ps`, `make down`) |
| `compose.checks.yaml` | Isolated API and web checks (`make check`) |
| `compose.browser.yaml` | Deterministic and signed-in Playwright suites |
| `compose.perf.yaml` | Release-mode override for `make perf-baseline` |
| `compose.prod.yaml` | Production services deployed by the release workflow |

Dockerfiles and their per-image ignore rules live in `docker/api/` and
`docker/web/`. Their build contexts are still `apps/api/` and `apps/web/`;
Dockerfile `COPY` paths are relative to those contexts.

`scripts/` contains the shell entry points used by the root Makefile.
[`perf/`](perf/README.md) contains the benchmark runner, SQL fixtures, and
reporting code.

See [the shared production Traefik contract](SHARED-TRAEFIK.md) before changing
edge routing or deployment.

## Email validation

The API uses the container's configured DNS resolver before sending sign-in
emails and Space invitations. The production API needs working DNS as well
as SMTP. A DNS failure asks the user to retry; the API doesn't probe individual
mailboxes. Local stacks using the `mailpit` relay accept synthetic
`@example.test` recipients without a DNS lookup.

## Web Push

Set these together in `.env.production` in the server's deployment directory:

```dotenv
WEB_PUSH_PUBLIC_KEY=<VAPID public key>
WEB_PUSH_PRIVATE_KEY=<matching VAPID private key>
WEB_PUSH_SUBJECT=mailto:admin@example.com
```

Use the unpadded base64url keys generated by `web-push generate-vapid-keys`.
Use a real contact address, keep the private key out of Git and logs, and
keep the key pair stable across deployments. Use a separate pair for
non-production. Missing or mismatched settings leave Web Push disabled.
Apply the migrations before starting the new API image. The API needs
outbound HTTPS access to the supported browser push services.

Verify on the deployed HTTPS build: open Horizon from the iPhone Home Screen,
register the device in **Settings**, and confirm that both a Calendar reminder
and a Task reminder arrive with the app closed. Check notification taps and
repeat on desktop before announcing support.

For local desktop testing, use a separate key pair in the root `.env`, then
run `make up-push` and `make migrate`. Open
`https://horizon.localhost/settings` in a browser that trusts the local CA.
After testing, disconnect the device and unregister the local service worker
in browser developer tools before returning to normal `make up` development.
